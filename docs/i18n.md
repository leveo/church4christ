# Internationalization (i18n)

The interface ships in twelve languages from one codebase: English (`en`), Chinese (`zh`),
Spanish (`es`), Brazilian Portuguese (`pt`), French (`fr`), German (`de`), Japanese (`ja`),
Korean (`ko`), Malay (`ms`), Indonesian (`id`), Vietnamese (`vi`), and Hindi (`hi`). The ten
newer translations are AI-assisted (community review welcome), and English is the final fallback. Words come from **three sources**, each with its own
mechanism, and a Chinese reader can flip the whole page from Simplified to Traditional
characters in the browser. This document is the technical reference; the church-facing
overview is [`docs/features/i18n.md`](features/i18n.md).

## Locales, languages and routing

Three terms, kept distinct:

- **Supported** languages are the ones the code base can render. They are entries in the
  registry, `LOCALE_REGISTRY` in `src/lib/locales.ts`: `code`, BCP-47 tag (`en`, `zh-Hans`),
  `hreflang`, Intl locale (`en-US`, `zh-CN`), Open Graph locale, native name, script
  (`latin`/`han`/`kana`/`hangul`/`devanagari`), and a CJK flag. Today: `en`, `zh`, `es`, `pt`
  (BCP-47 `pt-BR`), `fr`, `de`, `ja`, `ko`, `ms`, `id`, `vi`, `hi`.
- **Enabled** languages are the ones an installation actually serves, a non-empty subset of the
  supported set. The **default** language is one of the enabled languages.
- The **fallback chain** is *requested → default → `en`*. `t()`, `i18nJoin`, content
  collections, and email template lookup all follow it, so a missing translation is replaced by
  the next language in the chain instead of a blank.

Installation-wide settings (rows in the global `settings` table, not per campus):
`locale.enabled` (JSON array, e.g. `["en","zh"]`) and `locale.default`. They are read per
request by the middleware (`src/lib/localeSettings.ts`, memoized per isolate for 60 seconds) and
exposed as `Astro.locals.locales` (`{ enabled, default }`). Saving validates *default ∈ enabled ⊆
supported, at least one*. **Upgrade safety:** if the `locale.enabled` row is absent, the
installation is legacy: enabled = `en`, `zh`; default = `en`; an old `locale.default` row (it
was never read at runtime) is ignored until the settings are saved. Administrators edit both in
**Settings → Languages**; setup and onboarding write both rows for a new installation.

Routing (all in `src/middleware.ts`):

- Public URLs are prefixed by locale, `/en/…` and `/zh/…`, served by `src/pages/[locale]/`.
- A supported but **disabled** locale prefix is redirected (302, GET/HEAD) to the same path in
  the default locale. An unknown code is not a locale segment and 404s as before. Private
  Learning routes stay strict: a non-canonical locale segment is an opaque 404.
- A bare `/` is negotiated: the `c4c_locale` cookie (set **only** when the visitor uses the
  language switcher), then `Accept-Language` over the **enabled** set, then the default. The
  redirect sends `Vary: Accept-Language, Cookie`.
- The switcher (`LocaleSwitch.astro`) lists the enabled languages and links to the **same page**
  in each; links carry `?setlang=<code>`, which the middleware turns into the cookie and a clean
  redirect. More than three enabled languages collapse into a dropdown.
- Redirect targets built from request data go through `sameOriginTarget`
  (`src/lib/safeRedirect.ts`) so `//host` style paths can never leave the origin.
- SEO (`src/lib/seo.ts`, `Base.astro`): canonical, `hreflang` alternates, sitemap, `og:locale`,
  and `<html lang>` come from the registry over the enabled set; `x-default` is the default
  language. A page that is showing another language's content can pass `contentLocale` to
  `Base` so its canonical points at the original and it drops out of the fallback locale's
  alternates.

Formatting uses the registry too: `src/lib/dates.ts` (Intl with the registry tag; Han locales
keep the numeric-unit style), `src/lib/money.ts`, and helpers such as `listSeparator`,
`nameWithRole`, `pickByLocale`, and `pickPair` (the `*_en`/`*_zh` column pairs used by Service
Planning: Chinese prefers `zh` then `en`, every other language `en` then `zh`). Behavior that
is genuinely Chinese-specific, the Simplified→Traditional toggle and the Han-text editorial
heuristic, stays gated on `isChinese(locale)`.

## Source 1 — UI dictionaries (fixed labels)

Buttons, menus, and other fixed interface strings live in typed dictionaries, one file per
language:

- `src/i18n/en.ts` is the source (always bundled, the final fallback) and `src/i18n/zh.ts` is
  bundled too. Every other language is `src/i18n/<code>.ts`, loaded lazily through a dynamic
  import in `src/lib/i18n.ts`, so each ships as its own chunk (the build output lists them). A
  language that is still being translated exports an **empty partial dictionary**: nothing breaks,
  every key falls back to English.
- A locale file exports three things: the flat dictionary (`default`), partial overrides for the
  per-surface "design" copy (`design`, see below), and translated capability/readiness copy
  (`catalog`).
- `t(locale, key, vars)` is synchronous. It walks the fallback chain for the first dictionary
  that has the key and interpolates `{vars}`, **HTML-escaping** the interpolated values (see
  [`SECURITY.md`](../SECURITY.md)). The middleware awaits `loadDict(locale)` for the request
  language, and code that writes in another language (emails) awaits it too.
- **Design copy.** The `src/i18n/design*.ts` files hold English and Chinese for specific
  surfaces beside the components that read them. Every other language adds a partial override per
  section in its locale file (`export const design = { care: { ... }, finance: { ... } }`, typed
  against the English keys in `src/i18n/designRegistry.ts`); missing keys fall back along the chain.
- **Catalog copy.** Capability and preset names and descriptions (`config/capabilities.json`) and
  readiness check text (`config/readiness.json`) are `{ en, zh }` there (both required by the
  validators, which also accept any other supported language code). Translations for the other
  languages live in `src/i18n/catalog/<code>.json`
  (`{ "capabilities": { "<key>": { "label", "description" } }, "presets": { ... },
  "readiness": { "<id>": { "title", "description", "remediation" } } }`). The `modules.*`
  dictionary keys are generated from it, so a translator writes that copy once. The generated
  documentation (`npm run docs:generate`) stays English and Chinese. `config/editions.json`
  (repository README marketing for each edition) stays English and Chinese; it is not product UI.

**Quality is enforced by tests and a script.** `test/i18n.test.ts` and
`test/node/i18nKeysUsed.test.ts` run the same rules for every language, and
`node scripts/i18n/check.mjs [--locale es] [--strict]` runs them from the command line. A language
is either **complete** or listed in `config/i18n-status.json` (`inProgress`). Complete languages
need every English key (dictionary, design sections, catalog copy), identical `{placeholders}`
and HTML tags, non-empty values, no value left identical to English (except the allowlist in
`config/i18n-allowlist.json`: product names, codes, cognates), and the right script (`zh` Han,
`ja` kana or Han, `ko` Hangul, `hi` Devanagari; Latin-script languages may not contain Han,
kana, Hangul, or Devanagari). Nav and button labels more than 1.6 times the English length
produce a warning, never a failure. In-progress languages are still held to the structural rules
for whatever they do supply (no unknown keys, no placeholder drift, no empty values).

## Source 2 — Database content (editable, per-language)

Editable content that staff type in — ministry names, event titles, announcements — is
stored in **companion `*_i18n` tables**, one translation row per language, rather than
extra columns on the base row.

A query joins the base table to its `*_i18n` table once per link of the fallback chain
(requested, default, `en`; one join when they coincide) and `COALESCE`s each field, so a missing
translation falls back instead of rendering blank. One helper builds these joins (`i18nJoin` in
`src/lib/db.ts`, which accepts a locale or an explicit chain). Admin forms render translatable
fields with the reusable tabbed component `src/components/admin/LocaleFields.astro`: one tab per
**enabled** language, the default first. Field names stay `<field>_<code>` (`title_en`,
`title_zh`), so server handlers are unchanged, and a disabled language's stored text is kept in
a hidden input so saving a form never deletes a translation. Disabling a language never deletes
content. Editors for the `*_i18n` tables (events, announcements, custom pages, ministries, teams, service
types) also load and save every language beyond the en/zh columns through
`src/lib/i18nExtras.ts` (`loadExtraI18n`, `saveExtraI18n`, `localeValues`), and navigation links
and the identity settings (`site.name`, `site.tagline`, `site.service_times`, one key per
language) accept any supported language. Content kept in `*_en`/`*_zh` **column pairs** —
Service Planning, giving funds, registration events and their questions, group special events,
newcomer configuration labels, page-builder text, and the role names in the new-ministry
wizard — has no place to store a third language: those editors show only the en/zh pair (the
`only` prop of `LocaleFields`, `PAIR_LOCALES`) and every other language reads the English
text through `pickPair`. Moving those pairs to `*_i18n` tables is recorded debt.

Page-builder text and custom navigation labels are JSON maps `{ "<locale>": "text" }`. They are
validated against the **supported** registry (`parseLocaleText`): an unknown key is rejected,
a supported-but-disabled key is kept, and legacy `{ "en": …, "zh": … }` data validates unchanged.

The important property: **adding a language means inserting rows, never adding columns.**
The database shape is fixed no matter how many locales you support.

Public English prayer pages select only sheets explicitly marked `en`; Chinese pages
retain access to all published sheets. The same language scope applies to the latest
sheet, archive dates, and dated pages. Unlabelled legacy sheets stay off English pages.
Public English testimony pages likewise show only submissions marked `en`; Chinese pages
show both languages, with Chinese submissions first. The fixture's shared names, household
and group labels, schedules, event locations, and Learning titles use English defaults.
Existing user records are not rewritten, and locale-specific Chinese fixture content remains.

**Legacy editorial content (the Han rule).** Sermons, bulletins, and plan subtitles have no
source-language field, so a display heuristic checks for Han characters. It only counts as
evidence of Chinese content for readers of a **Latin-script** language (`en`, `es`, `fr`, ...;
`hidesHanRows` in `src/lib/editorialLocale.ts`): those pages omit rows whose editorial text
contains Han. For `zh` and for every non-Latin-script language (`ja`, `ko`, `hi`) nothing is hidden
by the heuristic, because Japanese and Korean text legitimately contains Han characters. Rows
that carry an explicit locale (prayer sheets, testimonies) never use the heuristic: they match the
reader's language along the fallback chain, and Chinese pages show them all. The paragraphs below
describe the Latin-script behavior, written for English.

Sermons currently have no source-language field. Until explicit metadata is available,
English public pages omit sermons containing Han characters in their title, scripture,
or series. This is a display heuristic, not language detection or translation: it can
also omit bilingual editorial content and cannot identify a video's spoken language.
Speaker names and stored content remain unchanged. Chinese pages include both languages.
The latest sermon, archive years, and year/month listings use the same rule; if newer
sermons are excluded, the home page finds the most recent eligible earlier sermon.

Bulletins also lack source-language metadata. English latest, archive, service tabs, and
dated reads select whole publications whose editorial fields contain no Han: service-time
label, program item/content, offering and attendance labels/values, memory verse, flowers
note, and announcement title/body/link label. Latest selection searches older publications
for each service, and the archive's 52-entry cap applies after eligibility. Chinese pages
keep both languages. Dedicated program-person and roster-name fields are never filtered.
This heuristic can omit bilingual prose or an otherwise English editorial note containing
a Han name; it cannot infer language reliably. Explicit editorial source metadata is the
future remedy. Nothing rewrites the original sheet or its announcements.

Serving plans keep their identities and scheduling data in every locale. `planDb` returns
raw `title`/`series` plus `display_title`/`display_series`; English views omit optional
editorial subtitles containing Han, while the date and localized service name still label
the plan. Chinese views retain the original subtitles. Names, assignment IDs, decline and
blockout reasons, and other member messages remain unchanged. Display fields must not be
used to populate editing forms or saved back over the originals.

## Source 3 — Content collections (Markdown prose)

Longer prose pages — "About", "Plan a Visit", beliefs, privacy, the pastor's articles,
fellowship and staff entries — are Markdown files in Astro **content collections**:

```
src/content/{pages,articles,fellowships,staff}/{en,zh}/<slug>.md
```

`src/content.config.ts` defines each collection's frontmatter schema (validated at
`astro check`). `src/lib/content.ts` loads an entry for the requested locale and, when the
translation is missing, **falls back to English and shows a "not translated" badge** rather
than a blank page.

## Simplified → Traditional toggle

Chinese content is authored once, in **Simplified** characters. Readers who prefer
**Traditional** characters flip the whole page with a toggle; the conversion happens **in
the browser**, instantly, and the choice is remembered. No second copy is stored.

- `src/lib/s2t.ts` (`toTraditional`) with the generated table `src/lib/s2t-table.json`
  (built by `scripts/generate-s2t.mjs` from `opencc-data`).
- `src/lib/zh-client.ts` is the small client script that performs the toggle.

## Emails follow the reader

Transactional emails (magic links, scheduling requests, the weekly digest) follow
`src/lib/emailLocales.ts`: the recipient's saved language when it is **enabled**; otherwise,
only when **exactly two** languages are enabled, both stacked (for en+zh the historical
Chinese-then-English layout); with one enabled language that language; with three or more the
default alone. Never more than two languages in one message. `email_templates` lookups fall
through the chain. See [`docs/features/email-automation.md`](features/email-automation.md).

## Add or translate a language

The ten languages `es`, `pt`, `fr`, `de`, `ja`, `ko`, `ms`, `id`, `vi`, and `hi` are already wired
up end to end: registry entries, `config/locales.json`, a lazy loader, an empty dictionary file,
an empty catalog file, a `supported_locales` row (migration `0041` seeds exactly these twelve),
font stacks, and the onboarding and settings language lists. **Translating one is purely
data**, in this order:

1. **Glossary.** Fill your language's column in [`docs/i18n/glossary.md`](i18n/glossary.md) first
   (and note the denomination or region you assumed). Reviewers check it; every later step uses it.
2. **Export the source.** `node scripts/i18n/export-keys.mjs --out keys.json` writes English (the
   source) and Chinese (reference) for the dictionary, the design sections, and the catalog copy;
   add `--locale es --missing` to get only what is left.
3. **Dictionary.** Fill `src/i18n/<code>.ts`: the exact keys of `en.ts` (leave the generated
   `modules.*` spread alone), same `{placeholders}` and HTML tags, natural church wording. The
   placeholder is typed `Partial<Record<keyof typeof en, string>>` (unknown keys fail `astro
   check`); once the language is complete, change it to `Record<keyof typeof en, string>` so a
   missing key becomes a compile error too.
4. **Design copy.** Fill the `design` export in the same file, one object per section
   (`care`, `careTools`, `content`, `finance`, `frontdoor`, `gatherings`, `member`, `ministry`,
   `operations`, `public`) with every key of the English section.
5. **Catalog copy.** Fill `src/i18n/catalog/<code>.json`: every capability, preset, and readiness
   check.
6. **Allowlist.** Text that is genuinely the same as English (a cognate, a product name) goes in
   `config/i18n-allowlist.json` under `locales.<code>`; never leave an untranslated copy instead.
7. **Validate.** `node scripts/i18n/check.mjs --locale <code> --strict` must report zero errors
   (warnings about long nav or button labels are advisory: check them on screen).
8. **Mark it complete.** Delete the language's line from `inProgress` in
   `config/i18n-status.json`. From then on `test/i18n.test.ts` and
   `test/node/i18nKeysUsed.test.ts` hold it to the full rules, and onboarding stops flagging it.
   Run `npx vitest run test/i18n.test.ts test/node/i18nKeysUsed.test.ts test/node/i18nCheck.test.ts`.
9. **Content.** Optional: Markdown under `src/content/{pages,articles,fellowships,staff}/<code>/…`
   and translated rows. Anything missing falls back along the chain.
10. **Review.** Label the translation "AI-assisted, community review welcome" when it was machine
    assisted, then enable the language in Settings → Languages and walk a page through the
    switcher on a phone-width screen (Japanese, Korean, and Hindi in particular: check line breaks
    and the system font).

### Adding a language that is not in the list

1. **Registry.** Add the entry to `LOCALE_REGISTRY` and `SUPPORTED_LOCALES` in
   `src/lib/locales.ts` (BCP-47, hreflang, Intl tag, Open Graph locale, native name, script,
   CJK flag) and to `config/locales.json`. `test/node/setup/locales.test.ts` fails if the
   two disagree.
2. **Files.** Create `src/i18n/<code>.ts` and `src/i18n/catalog/<code>.json` like the existing
   placeholders, register a loader in `src/lib/i18n.ts`, add the code to `inProgress`,
   `config/i18n-allowlist.json` (`locales`), and the imports in `test/helpers/i18nData.ts` and
   `scripts/i18n` (they read the supported list from `config/locales.json`).
3. **`supported_locales` row.** `INSERT INTO supported_locales (code) VALUES ('xx')` on each
   database, preferably in a new forward migration so every installation gets it.
4. **Fonts.** Add a script entry to `type.scriptFonts` in `design/foundation.json` if the
   system fonts do not cover the script, and extend the CJK line-height rule in
   `src/styles/base.css` if needed. Then `npm run tokens`.
5. **Verify.** `npm run check`, `npm run build`, and the suites that touch languages
   (`test/i18n.test.ts`, `test/locales.test.ts`, `test/localeSettings.test.ts`,
   `test/localeMiddleware.test.ts`, `test/seo.test.ts`), then enable the language in
   Settings → Languages.

The Simplified→Traditional toggle is Chinese-specific and needs no equivalent.

**Onboarding.** The local onboarding page (`scripts/onboard/web`) keeps its own wording in
English and Chinese only; it lists every supported language by native name for the *site*
and flags the ones whose translation is still in progress.

## README translations

The repository README exists in every supported language: `README.md` (English, the authoritative
version and GitHub's default) and `README.<code>.md` for the other eleven, linked from a language
bar at the top of each file. They live in the repository root so their relative image and
documentation links match the English file. The translations are AI-assisted and follow the
glossary in `docs/i18n/glossary.md`.

When `README.md` changes, update the translations in the same pull request where you can. If you
cannot, the English README stays authoritative; note the gap in the pull request so a translator can
follow up. Code blocks, link targets, and image paths must stay identical to the English file, and
in-page `#anchor` links must point at the translated heading. The generated capability table is
copied without its `capabilities:start` / `capabilities:end` markers, so only the English README is
regenerated by `npm run docs:generate`.
